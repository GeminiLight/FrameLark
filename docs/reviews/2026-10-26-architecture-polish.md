# 2026-10-26 共享编辑与项目存储打磨

本轮基于 `5db2518`，落实此前架构审查发现的可复现问题。目标是让 Web、CLI 和 Skill 在连续编辑、历史恢复和并发协作中保持相同含义。

## 改动与职责

| 问题 | 本轮处理 | 约束 |
| --- | --- | --- |
| 组图传对象给只接受 ID 的项目入口 | 显式 `openProject(id)`，入口校验，回归覆盖生产回调 | `load` 保留兼容别名 |
| 合法大文档无法保存为命名版本 | Web/Skill 共用容量定义；HTTP 413 返回明确代码 | 文档仍是 1 MiB |
| 历史反复复制大笔刷资源，几次编辑就触顶 | 单个 project.json 内按 SHA-256 复用文档及蒙版 | 磁盘 4 MiB、展开 128 MiB；不删版本 |
| 替换/删除范围无法回收蒙版槽位 | 事务末按可达引用回收，保留共享/间接引用 | 历史快照与撤销保持完整 |
| 保存和撤销分别占用状态，取消责任不清 | controller 统一保存/历史恢复所有权；持久化协议提取为 adapter | 切换照片不串历史，移出照片取消操作 |
| 慢渲染占用写锁，元数据依赖图像库 | 诊断、任务包、审核、审核后接受分准备/提交；图像依赖按需载入 | 提交重新核对 revision 与整个项目身份 |

## 数据迁移

小项目维持原 schema 2/3 记录。写入记录超过 512 KiB 时启用 schema 4 存储封装；已使用封装的项目后续继续使用。读取只展开，不写盘。每份快照独立复制，改当前版本不会改历史版本。

格式升级前保存旧文件原字节；同名备份已存在且不同则增加内容校验后缀，禁止覆盖。完整记录先验证容量和资源引用，再以临时文件、同步落盘和重命名提交。错误不替换原记录。缺资源、校验不符和超量展开均明确拒绝。

旧程序不识别 schema 4，须同步升级 Web/CLI/Skill。备份是升级前快照，不包含后续操作；不要把它当成无损降级工具。历史仍返回完整视图，未来大规模项目应另外设计分页和显式归档，不能用静默裁剪解决。

## 验证

- 完整测试 816/816 通过，无失败或跳过；包括现有 33 项图像效果回归。
- 连续 300 次范围修改、删除/撤销/重建、共享与间接引用、蒙版版本超过 10000 后的多命令事务。
- 实际 HTTP 命名版本接受大于旧 200 KB 上限的合法配方；超限 413 不改变文件。
- 8 个各 600 点笔刷的配方连续 12 次接受，保存所有旧版本和用户选择，项目记录小于 1 MiB；迁移目录后预览像素/画幅校验相同。
- 资源损坏、缺引用、展开超限、别名隔离、升级原字节备份和失败写入保全。
- 暂停真实预览结果提交时并发修改意图，诊断/审核/任务包/接受均允许编辑并拒绝过期提交；取消不写入；未改 revision 的外部记录变化同样拒绝。
- 禁止加载 sharp/canvas 的子进程中读取和修改项目元数据成功。
- 日常 Chrome 验证组图→单图→新增步骤→撤销→重做；同一路径纳入现有浏览器 CI。
- 46 个共享模块、架构边界、知识索引、插件与发布包检查随 PR 验证。

## 边界

本轮改善可靠性、状态所有权和重复资源成本。没有替换摄影渲染内核、调用付费模型或宣称新的审美评分提升。app.js 仍协调大量界面流程；本次抽离持久化协议并统一写入所有权，后续可继续按照片会话、组图和视图拆分。带保护参考的文件验证和部分旧操作仍在锁内，未宣称所有 I/O 均已移出。正式 Release 发布与用户已安装插件升级另行进行。
