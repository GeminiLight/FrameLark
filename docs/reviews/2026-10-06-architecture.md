# 架构与软件质量审核

审核基线：`f130dfc`。当前没有待合并 PR。检查范围包括浏览器状态、项目协作、导出、后台渲染、Web/Skill 边界与现有验证流程。

## 修复前的判断

| 优先级 | 问题与证据 | 用户影响 | 处理方式 |
| --- | --- | --- | --- |
| 高 | `app.js` 的照片状态在编辑器与照片列表中分别维护，通过三处字段复制同步 | 新字段或异步更新容易漏同步，切图、保存与导出可能使用不同状态 | 照片对象持有状态，编辑器读取当前照片的投影；历史记录与界面状态各有归属 |
| 高 | `project-workspace.js` 用全局 `updating` 抑制所有照片的保存调度 | 打开或更新一张照片期间，另一张照片的新修改可能没有被标记为待保存 | 把更新范围限制到具体照片，验证跨照片保存与失败恢复 |
| 高 | `ProjectBridge.render` 每个请求创建一个 Worker，没有并发或等候上限 | 重复预览、大图处理可能同时占用大量内存；关闭与取消的资源回收不集中 | 单一渲染调度模块限制并发、等候、期限与生命周期 |
| 中 | `makeExport` 混合界面协调、像素处理、编码与下载；文件项目分支没有执行浏览器分支的缓存限制 | 两种导出来源具有不同的资源规则，边界难以单独验证 | 拆出导出服务，统一缓存预算与取消规则 |

没有发现需要改换前端框架的证据。共享像素管线已有独立模块和一致性检查；项目候选、版本、保护与审核规则有明确归属，应保留这些边界。现有界面与专业能力是回归验收的依据。

## 本轮实施范围

1. 统一活动照片的状态来源，清除字段复制。
2. 隔离每张照片的项目更新与保存调度。
3. 集中后台渲染的资源管理。
4. 从界面中拆出导出处理服务，并校准资源限制。

每一项先复现或建立行为验证，再修改实现。像素算法、项目数据格式、导航和风格选择沿用现有契约。工具结果投影也从 HTTP 路由中独立出来；结构检查会阻止运行模块反向依赖路由，以及浏览器引入 Node 专用代码。

导出实测还发现确认按钮可能位于弹窗可视区域之外。主要操作已固定在弹窗底部，并按桌面、短屏和手机检查实际点击位置。

## 验证与结论

- 跨照片保存问题已先复现：打开第二个项目期间，第一张照片修改后仍被判断为无需保存；改为按照片隔离后通过回归检查。
- 真实渲染比较：同样五个预览请求，旧实现同时创建五个线程，新实现最多两个；五个请求均完成，输出像素哈希逐一相同。
- 完整测试 432 项通过，新增检查覆盖状态所有权、跨照片保存、渲染并发/取消/失败/关闭，以及两种导出的缓存和流取消规则。
- 导出浏览器验证覆盖：两张照片分别调整，导出时继续编辑并切图，成片保持点击时的版本；浏览器与文件项目生成的真实 PNG 像素、尺寸均与对应预览一致。
- 原有导航与协作浏览器检查通过，学习、偏好、风格、我的、顾问、命名版本与逐项接受保持可用。导出确认在 1280×577、390×844、320×720 下可见且命中实际按钮。
- Web/Skill 29 个共用处理与尺寸模块一致；插件分发检查通过，仍包含 146 个源码文件。

结论：本轮高优先级边界问题已修复，适合完成持续集成后合入。验证使用授权测试照片和模型协议夹具；未调用新视觉模型，也不把工程通过等同于新的摄影审美或画质改进。

## 后续结构工作

顾问对话与样式表仍是较大的协调区域。它们应在明确状态所有权后按独立流程继续拆分；样式整理需以桌面、手机截图与交互验证为依据，避免覆盖规则迁移时改变已有布局。
