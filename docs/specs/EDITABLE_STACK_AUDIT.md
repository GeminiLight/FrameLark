审查日期：2026-10-06。基线为 #21 的 `fb4a612`，它包含已更新并合并的 #16，以及 #17–#21 的编辑栈实现。本次检查使用公开示例图，不处理私人照片。

## 判断

- **CI**：基线 #21 的 push 与 pull_request 两次运行中，container、web、test 全部成功。新增修复和优化也需要在其最终提交上通过同一套检查。
- **模块化**：新增编辑核心已实现真实的步骤组合、独立参数与范围、按顺序执行和独立撤销。应用层协调代码仍集中，旧调整保留为兼容基础，不能把它称为全应用已完全拆解。
- **普通用户体验**：步骤列表和前后对比可理解；入口重复、过长的参数面板和两种保存交互仍增加理解成本。现阶段适合试用，尚需一次集中简化。
- **性能**：本次优化有实际收益，尤其是曝光和中间步骤修改；长栈在 1400 像素下仍达不到连续拖动的流畅程度。

## CI 与真实缺陷

基线通过记录：

- [#21 PR 检查](https://github.com/GeminiLight/FrameLark/actions/runs/37381743721)
- [#21 push 检查](https://github.com/GeminiLight/FrameLark/actions/runs/37381738809)

#17、#19、#20 的当前提交检查成功。#18 的同一提交存在历史失败记录和后续成功重跑，不能把历史失败说成不存在，也不能用一次重跑证明早期分支没有偶发问题。最终实现包含后来在 #19 修复的 IndexedDB 配额错误处理，以及 #21 的项目能力重试。合并顺序仍是 #17 → #18 → #19 → #20 → #21；本次新增 PR 接在 #21 后。

本轮发现并修复的错误：

1. **兼容参数重置未改变文档**。原按钮只修改 `manual` 投影，而渲染以文档基础为准，导致滑杆归零但照片效果保留。现在通过 `ReplaceLegacyBase` 保存，同时保留基础中的风格、局部调整及独立步骤，并同步滑杆与数值。真实网页验证重置、撤销、重做、刷新，再由独立 CLI 读取文档确认基础曝光为 0，两个步骤及其启用状态、强度、蒙版不变，原片字节校验不变。
2. **色相转换缺失第六区间且第五区间排列错误**。红色跨过 0° 时可能报错，蓝紫色可能映射错误。已修正六区间转换，并用独立 HSL 插值公式验证六种色相输入。这是未合并的新管线中的算法错误修复，涉及这些色相/明度调整的结果会纠正，不能把这一部分描述为仅性能变化。
3. **保存失败后仍能拖动参数**。普通命令已阻止继续编辑，但拖动预览未遵守同一限制，重试旧请求时可能覆盖后续拖动。现在步骤和兼容参数在重试前禁用，重试按钮仍可用。回归测试覆盖失败 → 尝试拖动 → 原配方保留 → 同一请求重试 → 单次撤销记录。

本地最终验证：491/491 测试通过；共享引擎、架构边界与独立插件打包检查通过。远端网页检查继续包含导航、协作和导出流程，未删除或放宽门槛。新增提交的远端结果以对应 PR 的当前提交检查为准。

## 模块边界与证据

| 边界 | 实现与检查 | 尚存限制 |
|---|---|---|
| 照片状态 | 每张照片拥有编辑文档；活动界面是投影，异步保存和历史归属原照片 | 应用协调仍在约 3800 行的 `app.js` 中 |
| 编辑工具 | 曝光、影调、色彩、细节、氛围具有参数边界、版本和执行内核 | 单个工具内含相关参数；不是每个滑杆一个工具 |
| 编辑命令 | 添加、修改、暂停、强度、范围、排序、删除等统一编译后提交；失败不部分写入 | 少数旧交互仍需适配，本次重置修复就是一个实例 |
| 蒙版 | 独立且带版本的范围资源，实时输入与冻结原片引用明确；组合、共享更新与依赖校验 | 几何/明度范围不等于语义分割，冻结引用目前仅支持原片 |
| 渲染 | 按步骤执行 Float32 工作缓冲，最后一次编码；排序实际改变结果 | 解码与兼容基础仍是既有 8 位路径 |
| 持久化 | 网页草稿与文件项目使用同一文档；文件保存需预览凭据与版本检查 | 旧调整被固定在兼容基础，无法恢复历史原子操作 |
| 多入口 | 网页与独立 Skill 的 41 个处理模块一致，检查器与队列副本也有一致性检查 | 副本分发仍靠构建检查，尚非单一发布包 |

已有行为测试覆盖独立节点修改不改变其他节点、真实排序效果、实时/冻结蒙版差异、风格展开、部分接受、跨照片保存、取消任务、缓存身份与预算等。本轮新增改动前像素基准覆盖每种工具、混合栈、透明像素、蒙版和带旋转的取样网格，校验优化后 RGBA 一致。

## 普通用户视角

真实网页试用可完成选步骤、调参数、暂停、蒙版查看、保存与撤销。以下是需要继续简化的具体问题，未在本次做大范围界面重排：

| 优先级 | 普通用户遇到的情况 | 建议 |
|---|---|---|
| 高 | 影调一次展示 10 个参数，色彩更多；移动、删除、修改此步骤在底部，需长距离滚动 | 将步骤操作放到选中行附近，曲线、色彩混合等默认折叠 |
| 高 | 顾问、交给 Agent 继续、协作精修之间的区别不够明显；文件项目与项目与记录进入同一管理功能 | 保留一个主要文字入口，将共享项目与高级协作放到次级菜单 |
| 中 | 手调保存期间短暂出现“试片等你比较”，但流程随后自动接受 | 对自己的自动保存显示保存进度，只对外部/模型候选显示比较提醒 |
| 中 | 当前照片已保存到文件项目，仍并列展示浏览器草稿；用户需理解两种存储方式 | 在一个保存状态入口解释位置，将其他草稿收进管理页 |
| 中 | “兼容基础”“线性明度”“允许超白中间值”要求用户理解内部概念；中性基础也叫“已有调整” | 普通文案解释实际效果，把数值与版本术语收进高级设置 |

建议的主流程仍是：**描述想法 → 查看若干独立步骤和实际对比 → 逐项接受 → 随时改参数、范围或撤销 → 导出**。手动工具是这条流程的微调入口。下一轮体验改动应围绕这条路径集中处理，而不是继续增加入口。

## 性能：已优化与剩余瓶颈

本次减少逐像素临时数组，复用双精度 RGB 临时值，预计算曝光倍率和褪色常数，使用等价的 8 位到 Float32 转换表；缓存按容量分散保留中间结果，并优先保留倒数第二步，最终 RGBA 仍单独缓存。缓存上限仍为 64 MiB，输出精度、原片身份、取消和预算规则保留。

同机 Apple M3、Node 22.22.2；固定合成渐变和曝光/影调/色彩/细节/氛围序列。完整协议与所有 1/8/24 步、560/1400 像素、首/中/末位置数据见 [benchmark-performance-audit.json](evidence/benchmark-performance-audit.json)。CPU 分析与计时分别运行，不将分析器的开销混进对比。每个位置先独立预热原配方，避免前一次修改影响后一位置。

| 1400 × 1050 场景 | 优化前 | 优化后 |
|---|---:|---:|
| 单步曝光首次渲染 | 703.7 ms | 282.6 ms |
| 8 步首次渲染 | 2743.4 ms | 1784.3 ms |
| 8 步修改中间步骤 | 2747.0 ms | 1079.3 ms |
| 24 步首次渲染 | 6733.7 ms | 4755.8 ms |
| 24 步修改中间步骤 | 6420.4 ms | 2455.0 ms |
| 24 步修改末尾步骤 | 461.3 ms | 320.2 ms |

560 × 420 的 24 步首次渲染从 1032.8 ms 降至 735.0 ms。1400 网格保留缓存约 55.86 MB，560 网格约 64.92 MB，均不超过 64 MiB；这些是缓存保留字节，不是进程峰值内存。完全相同的渲染命中最终缓存时仍约 94–103 ms，主要继续承担取样字节 SHA-256 校验。

这些是固定协议单次样本和三次相同配方热样本，说明优化方向与本机收益，不是跨设备延迟保证。首步改变需重算全栈；蒙版资源变化也会保守地使前缀失效。连续拖动期间取消任务会销毁 worker，不能假定每次都能获得离线基准中的预热缓存收益。风格缩略图仍同步执行多个配方，长栈下可能阻塞主线程。

下一步性能优先处理拖动期间较小网格的临时预览、释放后完整清晰预览，以及风格缩略图按需在 worker 中生成。导出和接受凭据继续使用完整结果；应分别测量首帧、释放后最终清晰帧与主线程阻塞，不能仅用缓存命中时间代替体验。
